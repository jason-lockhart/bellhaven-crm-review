# Assessment writeup

The application reconciles a public location inventory with CRM accounts, then makes changes only after human review. It keeps the original Flask, requests/BeautifulSoup, SQLite and React architecture so each part can be explained and modified during a 45-minute walkthrough.

Matching is deterministic and explainable. CRM billing fields are mapped to canonical address fields, exact physical location supports rebrands, and name similarity supplies additional evidence. Conflicting locations and unresolved corporate parents require investigation. Duplicates are linked and marked Inactive with notes; stale locations receive Needs Review. Neither is deleted.

Financial safety governs ownership corrections. Both positive revenue and positive AR require a verified successor account; the original parent and historical billing remain unchanged. Unknown financial values block writes. Approval rereads current identity, parent and financial data; GET verification follows every write. Stable creation markers and persisted successor IDs recover partial CHOW failures without a second successor. Atomic claims stop concurrent approvals. An uncertain POST outcome blocks further creation unless the marker can be recovered.

AI assisted the original generation and this source audit, targeted repairs, test design and documentation. It does not choose live changes or replace human evidence review. The audit found that initial field/name assumptions explained the missing-account and parent failures; an earlier partial adapter fix left bad pending SQLite proposals visible. Those are now superseded while historical decisions are retained. No live CRM corrections were made by the repair session.

Tradeoffs: conservative thresholds can leave manual investigations; parent resolution supports the assessment's known corporate labels rather than a universal corporate identity service. Basic authentication/private HTTPS access is appropriate for this small review tool but would become SSO and role-based authorization in production. SQLite is durable on one persistent host; ephemeral schedulers need a shared durable datastore. The external API offers no documented transaction/idempotency key, so uncertain creates deliberately stop for inspection. Interrupted approval locks require explicit operator recovery.

Next: calibrate thresholds against labeled real examples, add corporate aliases with source provenance, enrich change-of-ownership evidence, migrate to Postgres with worker leases, add reviewer identity and optimistic API concurrency if available, and monitor scan coverage/count drift. A completed submission also requires the candidate to apply reviewed corrections in the assessment CRM and record a short browser demonstration.
